## 核心理念

**准确是翻译的生命线**。本工具采用「章节级翻译」策略，确保：
- 每个章节作为完整语义单元翻译，保持上下文连贯
- 每一张图片都被保留，绝不丢失
- 技术细节精准传达，绝不曲解
- 术语在整个章节内保持一致

## 核心执行流程

### 步骤 1: 内容获取与解析 ⬜

> **🚨 推荐方案：使用 `web_fetcher.py` 脚本（支持网页和 PDF）**
>
> 该脚本支持：
> - **网页**: 使用 `html-to-markdown` (Rust 内核) + BeautifulSoup 预处理
> - **PDF**: 使用 PyMuPDF 提取文本内容
> 能正确处理复杂表格（单元格内列表）、保留完整文章结构。

#### 方案 A：使用 web_fetcher.py（推荐）

```bash
# 首次使用需安装依赖
pip install html-to-markdown beautifulsoup4 pymupdf

# 网页抓取
# SKILL_DIR = 本 skill 的 SKILL.md 所在目录，按实际安装位置解析，不要硬编码
python3 "$SKILL_DIR/scripts/web_fetcher.py" "${URL}" -o /tmp/fetched_article.md

# PDF 文件
python3 "$SKILL_DIR/scripts/web_fetcher.py" "/path/to/document.pdf" -o /tmp/fetched_article.md
```

脚本会自动检测输入类型（URL 或 PDF 文件）并使用对应的解析方法。

然后读取生成的 Markdown 文件作为原文基础。

#### 方案 B：使用 WebFetch（备选）

如果 web_fetcher.py 不可用，使用 WebFetch 工具：

```
WebFetch(url, "请完整提取这篇技术文章，要求：

【结构提取】
1. 文章标题（原文）
2. 作者、日期等元信息
3. 所有正文内容，按原始段落结构

【特殊元素】
4. 所有代码块：保持原样，标注语言
5. 所有图片：提取完整 URL 和 alt 文本，格式 ![alt](url)
6. 所有引用块：保持 > 格式
7. 所有链接：保持 [text](url) 格式
8. 所有列表：保持 - 或数字格式
9. 所有表格：保持原始格式，单元格内列表用 <br> 分隔

【关键要求】
- 逐句保留，不合并、不省略任何句子
- 图片必须全部提取，标记位置
- 表格单元格内的列表项用 <br> 连接，保持单行格式
- 输出纯 Markdown 格式")
```

> ⚠️ **WebFetch 已知问题**：复杂表格（单元格内包含列表）可能转换不正确，
> 建议优先使用方案 A。

**✅ 步骤 1 完成标志**：已获取文章标题、正文、图片 URL 列表

### 步骤 3: 图片处理 ⬜

**图片是技术文档的重要组成部分，必须 100% 保留。**

#### 3.1 图片提取与统计

首先，统计原文中所有图片：

```
从抓取的内容中提取所有图片：
1. Markdown 图片：![alt](url)
2. HTML 图片：<img src="url" alt="...">
3. 背景图片（如有）

输出图片清单：
- 图片1: url=xxx, alt=xxx
- 图片2: url=xxx, alt=xxx
- ...
- 共计 N 张图片
```

#### 3.2 图片下载

对每个图片 URL 下载到本地：

```bash
# 创建图片目录
mkdir -p output/${SLUG}/images

# 对每个图片执行（保留原始扩展名）
curl -L -o "output/${SLUG}/images/figure1.png" "${IMAGE_URL}"
```

#### 3.3 图片校验

下载完成后校验：

```
□ 下载成功：N 张
□ 下载失败：M 张（记录失败原因，保留原始 URL）
□ 总计：原文 N 张 = 下载成功 + 保留原 URL
```

**关键原则**：即使下载失败，也必须保留原始 URL，绝不丢弃任何图片引用。

**✅ 步骤 3 完成标志**：`images/` 目录下有下载的图片文件，数量与原文一致

### 步骤 4: 章节级翻译 ⬜

**这是整个流程最关键的步骤**。采用章节级翻译策略，在保证准确性的同时最大化翻译效率。

#### 翻译哲学 - 信达雅的优先级

```
信（准确）> 达（通顺）> 雅（优美）
```

**准确是前提**，没有准确，通顺和优美毫无意义。

#### 章节级翻译策略

> **核心思想**：现代大模型在处理完整语义单元时翻译质量更高，上下文越完整，术语一致性和行文连贯性越好。

**翻译粒度选择**（按优先级）：

1. **章节级别**（推荐）
   - 每个 `##` 或 `###` 标题下的完整内容作为一个翻译单元
   - 优点：语义完整，术语一致，风格统一
   - 适用：大多数结构清晰的技术文档

2. **段落组级别**（章节过长时）
   - 如果单个章节超过 3000 tokens（约 2000 个英文单词），按 3-5 个相关段落分组
   - 保持逻辑相关的段落在一起翻译

3. **合并短章节**
   - 如果相邻章节都很短（少于 500 tokens），可以合并翻译
   - 保持翻译的效率

**翻译执行流程**：

```
第一步：识别文章结构
  - 提取所有 ## 和 ### 标题
  - 评估每个章节的长度
  - 决定翻译单元的划分

第二步：按章节批量翻译
  - 一次性翻译整个章节（或段落组）
  - 在同一翻译单元内保持术语和风格一致
  - 不要逐句拆分，让大模型理解完整上下文

第三步：整体校对
  - 检查章节间术语是否一致
  - 确保图片、代码块、链接完整保留
```

#### 翻译原则

1. **语义完整性**
   - 翻译必须完整传达原文所有信息
   - 不省略任何细节，哪怕看起来"不重要"
   - 不添加原文没有的内容

2. **技术术语处理**
   ```
   首次出现：依赖注入（Dependency Injection）
   再次出现：依赖注入
   ```
   - 专有名词保留原文：React、Kubernetes、API
   - 通用术语翻译：function → 函数，variable → 变量
   - **同一章节内术语必须一致**

3. **句式转换**
   - 被动句转主动句（当更自然时）
   - 长句可拆分，但**必须保留所有信息**
   - 保持技术文档的客观语气

4. **数字和单位**
   - 保持原样：100ms、5GB、v2.0
   - 日期格式保持原样

#### 特殊元素处理

1. **代码块** - 绝对不翻译
   - 代码内注释：翻译
   - 代码本身：保持原样

2. **图片** - 必须 100% 保留
   ```markdown
   原文：![Architecture diagram](https://example.com/arch.png)
   翻译：![架构图](images/figure1.png)
   ```
   - alt 文本：翻译
   - 图片路径：替换为本地路径

3. **链接**
   - 链接文本：翻译
   - URL：保持原样

4. **引用块**
   - 保持 `>` 格式
   - 内容逐句翻译

5. **列表项**
   - 每个列表项独立翻译
   - 保持原有的层级结构

#### 输出文件

生成以下文件：

**original.md** - 原文
```markdown
# {原标题}

**Published:** {日期}
**Authors:** {作者}

---

{原文内容，图片路径替换为本地路径}
```

**translated.md** - 翻译版
```markdown
# {中文标题}

**发布日期：** {日期}
**作者：** {作者}

---

{翻译后的内容}
```

**✅ 步骤 4 完成标志**：已按章节级翻译生成 `original.md` 和 `translated.md`，图片数量、章节数量与原文一致，术语全文一致

### 步骤 5: 生成幻灯片元数据 ⬜

> **🚨 强制步骤：此步骤不可跳过**
>
> 必须生成 `slides_metadata.json` 文件，这是步骤 7（生成幻灯片图片）的前置依赖。

**核心原则：智能分块原文，不做总结压缩**

**关键转变**：从"提炼要点"转为"智能分块原文"，将原始内容完整传递给 AI 文生图模型。

#### 5.1 分块策略（全新方法）

将**翻译后的文章**按逻辑、章节、主题等原则分成 **3-6 个内容块**：

```
分块规则：
1. 基于文章的自然章节结构（## 和 ### 标题）
2. 每个内容块应是一个完整的逻辑单元（一个完整主题/概念）
3. 内容块之间有清晰的主题边界和递进关系
4. 优先保持逻辑完整性，而非机械平分字数
5. 一个内容块可以包含多个段落，只要它们属于同一主题
6. 块数量：3-6 块（严格上限），确保每块信息密度足够
```

**典型分块模式**：
- **问题-方案-实践** 三段式（解决方案类文章）
- **概念-架构-实现-优化** 四段式（技术深度文）
- **背景-核心机制-应用场景-最佳实践** 四段式（全面介绍类）

#### 5.2 内容块处理（关键变更）

对每个内容块，提取以下字段：

```
1. index: 序号（1, 2, 3...）【必须显式指定】

2. title: 该内容块的简短标题（8-20字，精准概括主题）
   示例："Agent Teams 核心概念与架构"

3. description: 该内容块的【完整原文内容】⚠️ 这是最关键的字段变更
   - 直接复制该块对应的翻译内容，一字不改
   - 包含所有段落、细节、数据、例子
   - 可以是几百字到上千字，完全没有限制
   - 保留原始的语句结构和表达
   - 不做任何总结、概括、提炼、压缩
   - 只做必要的格式清理：
     * 移除 Markdown 标记（#、*、`、[]()）
     * 代码块内容可保留关键部分
     * 保持分段和换行

示例对比：
❌ 旧方法："Agent Teams 是实验性功能，让多个 Claude 实例协同工作..."（150字总结）
✅ 新方法："Agent teams 是实验性功能，默认禁用。要启用它，请设置环境变量...关键组件：共享任务列表、消息邮箱系统、独立上下文..."（完整400+字原文）
```

#### 5.3 输出文件：slides_metadata.json

使用 **Write** 工具生成 `slides_metadata.json`：

```json
{
  "slides": [
    {
      "index": 1,
      "title": "内容块标题（8-20字）",
      "description": "该内容块的完整翻译原文，不做任何压缩。可能有几百字到上千字，包含所有段落、细节、数据点、例子、代码片段说明等。直接从 translated.md 中复制对应章节的完整内容，只做格式清理（移除 Markdown 标记），不改变任何语句和表达。"
    },
    {
      "index": 2,
      "title": "另一个内容块标题",
      "description": "继续完整复制下一个逻辑块的翻译内容..."
    }
  ]
}
```

**关键提醒**：
- `description` 字段是 AI 文生图的输入源，内容越完整，生成的幻灯片信息密度越高
- 严格 3-6 个内容块，每块应覆盖文章 20-35% 的内容
- **必须显式指定 `index` 字段**（1, 2, 3...），否则所有图片会覆盖同一个文件

**✅ 步骤 5 完成标志**：已生成 `slides_metadata.json`，包含 3-6 个内容块，每个 `description` 字段包含完整的原文分块内容

### 步骤 7: 生成 AI 幻灯片图片 ⬜

> **🚨 普通模式强制步骤：生成失败必须停止，不得继续构建空幻灯片预览**
>
> `generate_slides.py` 为每个内容块启动一个独立 `codex exec` 会话，默认 4 路并发，各会话内调用内置 `$imagegen`。Codex 把产物写进 `$CODEX_HOME/generated_images/<会话 id>/`，会话之间目录天然隔离，因此并发不会互相挑错图片。脚本不直接调用图片 API，也不读取任何图片 API Token。

#### 7.1 复制生成脚本

> **🚨 强制要求：必须复制脚本到工作目录**
>
> 脚本使用相对路径查找 `slides_metadata.json`、`slides/` 等文件，
> 必须在 `output/{slug}/` 目录内执行，否则会报错找不到文件。

```bash
# 将脚本从 skill 目录复制到输出目录
cp "$SKILL_DIR/scripts/generate_slides.py" output/${SLUG}/
chmod +x output/${SLUG}/generate_slides.py
```

#### 7.2 运行文生图脚本

```bash
cd output/${SLUG}
command -v codex
codex login status
python3 generate_slides.py
```

参数说明：
- `-i/--input`：元数据文件，默认 `slides_metadata.json`
- `-o/--output`：图片目录，默认 `slides/`
- `-a/--aspect-ratio`：写入提示词的目标画布比例，默认 `16:9`
- `-j/--concurrency`：并发的 Codex 会话数，默认 `4`；`-j 1` 退回串行
- `--dry-run`：只生成 `slides/prompts.json`，不启动 Codex CLI

#### 7.3 前置条件与失败处理

能够执行 `codex` 只是第一个条件。还必须满足：

- Codex CLI 已完成登录，`codex login status` 成功；
- 当前 CLI 版本和账号可访问内置 `imagegen` skill / `image_gen` 工具；
- 当前网络允许 Codex 完成图片生成。

脚本会把各会话日志按 slide 分段合并保存到 `slides/codex-imagegen.log`。如果 Codex CLI 退出异常、任一目标 PNG 缺失或格式无效，脚本返回非零，并保留原有整组图片不变。

失败时读取日志并向用户报告实际错误；不要继续步骤 8，也不要把只有占位卡片的 HTML 报告为完整交付。

**✅ 步骤 7 完成标志**：
- `generate_slides.py` 文件存在于输出目录
- `python3 generate_slides.py` 退出码为 0
- `slides/` 目录下每个元数据 index 都有对应的有效 `slide_XX.png`
- `slides/prompts.json` 和 `slides/codex-imagegen.log` 可用于审计

### 步骤 8: 生成 HTML 预览 ⬜

> **🚨 强制步骤：必须运行脚本，禁止手写 HTML**
>
> 必须复制并运行 `build.py`，不允许手动编写 HTML 文件。
> `build.py` 会正确处理 Markdown 渲染、幻灯片卡片、图片内嵌等逻辑。
>
> **注意：此步骤必须在步骤 7（生成幻灯片图片）之后执行，以便将生成的图片内嵌到 HTML 中。**

#### 8.1 复制构建脚本

> **🚨 强制要求：必须复制脚本到工作目录**
>
> `build.py` 使用相对路径读取 `original.md`、`translated.md`、`slides_metadata.json` 等文件，
> 必须在 `output/{slug}/` 目录内执行。

```bash
# 将脚本从 skill 目录复制到输出目录
cp "$SKILL_DIR/scripts/build.py" output/${SLUG}/
chmod +x output/${SLUG}/build.py
```

#### 8.2 运行构建脚本

```bash
cd output/${SLUG}
python3 build.py
```

脚本会读取以下文件并生成 `preview.html`：
- `original.md` → 原文内容
- `translated.md` → 翻译内容
- `slides_metadata.json` → PPT 卡片数据
- `slides/*.png` → AI 生成的幻灯片图片（如果存在则内嵌）

**✅ 步骤 8 完成标志**：
- `build.py` 文件存在于输出目录
- 已执行 `python3 build.py`
- `preview.html` 由脚本生成（不是手写的）
- 如果步骤 7 成功，幻灯片图片已内嵌到 HTML 中

## 最终检查清单

在向用户报告"完成"之前，必须确认以下所有项目：

```
□ output/{slug}/ 目录已创建
□ original.md 已生成
□ translated.md 已生成
□ combined.md 已生成
□ slides_metadata.json 已生成（包含 3-6 个幻灯片）
□ generate_slides.py 已复制到输出目录
□ 普通模式下 python3 generate_slides.py 退出码为 0
□ 普通模式下 slides/ 目录包含与元数据一一对应的有效 PNG
□ build.py 已复制到输出目录
□ python3 build.py 已执行（在生成幻灯片之后）
□ preview.html 由 build.py 生成（不是手写的，含内嵌图片）
□ images/ 目录包含下载的原文图片
```

**只有所有检查项都通过，才能向用户报告"完成"。**

## 参数说明

| 参数 | 说明 |
|------|------|
| `--no-ppt` | 显式跳过 AI 幻灯片生成（步骤 7），仍生成 slides_metadata.json 和带占位卡片的 preview.html |
| `--quick` | 快速模式，仅生成 translated.md |

---

## 错误处理

| 错误类型 | 处理方式 |
|---------|---------|
| 网页无法访问 | 提示用户检查 URL 是否正确 |
| 图片下载失败 | 记录失败图片，使用原始 URL，继续处理 |
| 翻译异常 | 保留原文，标记 `[待翻译]` |
| 找不到 `codex` | 停止步骤 7，提示安装 Codex CLI 并确认 PATH |
| Codex 未登录 | 停止步骤 7，提示运行 `codex login` |
| imagegen 不可用或图片缺失 | 读取 `slides/codex-imagegen.log`，报告真实错误并停止构建 |
| build.py 执行失败 | 输出错误信息，不要手写 HTML 替代 |

## 附录：为什么每个步骤都重要

| 步骤 | 如果跳过会发生什么 |
|------|------------------|
| 步骤 5 | preview.html 中的幻灯片栏为空 |
| 步骤 7 | 用户看不到 AI 生成的视觉化内容，体验大打折扣 |
| 步骤 8 | preview.html 无法正确渲染 Markdown 和幻灯片，或图片未内嵌 |

**每个步骤都是产品体验的一部分，不是"可选功能"。**

**关键顺序：步骤 7（生成图片）必须在步骤 8（构建 HTML）之前执行，否则 HTML 中不会包含内嵌的幻灯片图片。**
